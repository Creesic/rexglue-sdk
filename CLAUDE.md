## What this is

ReXGlue (SDK name `rexglue`) is a **static recompiler**: it converts Xbox 360 PowerPC game
binaries (XEX executables) ahead-of-time into portable C++ source that compiles and links into a
native x64 executable — no interpretation or JIT at runtime. It's built on the foundations of
[Xenia](https://github.com/xenia-project) (the Xbox 360 emulator) but replaces Xenia's runtime
PPC interpreter/JIT with an offline analyze-then-emit-C++ pipeline, in the spirit of
[XenonRecomp](https://github.com/hedge-dev/XenonRecomp).

`FM2/` in this repo is a concrete downstream project: the recompiled build of *Forza Motorsport 2*
game code, generated by and linked against this SDK. It is currently untracked in git (exists on
disk, no commits) — treat `FM2/generated/**` as build output, not hand-authored source.

## Build & test commands

Requires **Clang ≥ 18**, 64-bit host, C++23 (enforced with `FATAL_ERROR` in the root
`CMakeLists.txt` if violated). Only `RelWithDebInfo` is a supported config — Debug/Release presets
exist in `CMakePresets.json` but are explicitly disabled via the `vendor` block.

Day-to-day workflow uses the `PSReX` PowerShell module (`scripts/PSReX/`):

```powershell
Import-Module .\scripts\PSReX -Force
rex-setup                 # Invoke-ReXSetup: installs pre-commit hook, VS dev-shell profile, checks toolchain
rex-configure              # Invoke-ReXConfigure: cmake --preset <auto-detected>
rex-build                  # Invoke-ReXBuild: cmake --build out/build/<preset> --config RelWithDebInfo
rex-test                   # Invoke-ReXTest: ctest --preset <preset>-relwithdebinfo
rex-install                # Invoke-ReXInstall: cmake --install out/build/<preset> --config RelWithDebInfo
rex-format [-Modified|-All|<paths>]   # clang-format (default: git-modified + untracked files only)
rex-lint [-BuildDir <dir>]            # clang-tidy over include/ + src/, needs compile_commands.json
```

Preset auto-detection (`scripts/PSReX/Private/Get-ReXPreset.ps1`): `$env:REXGLUE_PRESET` overrides;
otherwise `win|linux` x `amd64|arm64` from `$IsWindows`/`$env:PROCESSOR_ARCHITECTURE`. Preset names:
`win-amd64`, `win-arm64`, `linux-amd64`, `linux-arm64`.

To run a single test, bypass the wrapper (it doesn't take a filter) and call ctest/the test binary
directly:
```powershell
ctest --preset win-amd64-relwithdebinfo -R "unit.SomeTestName"   # or "ppc.<case>"
out\build\win-amd64\RelWithDebInfo\unit_tests.exe "test name"
```

Tests are Catch2 (vendored at `thirdparty/catch2`), built only when `REXGLUE_BUILD_TESTS=ON`.
`tests/unit/` (codegen, core, kernel, memory, ppc, rexglue, system — prefix `unit.`) is normal C++
unit tests. `tests/ppc/` (prefix `ppc.`) is a self-hosting oracle: `cmake/ppc_test_pipeline.cmake`
assembles `tests/ppc/asm/*.s` with a vendored `powerpc-none-elf-*` toolchain (`tools/binutils`)
into real PPC binaries, then feeds them through the `rexglue recompile-tests` command so the
recompiler's own output becomes the generated Catch2 test cases — i.e. it validates PPC instruction
semantics by recompiling them, not by hand-writing expected values.

**FM2 is a separate CMake project**, not a subdirectory of the root build — it has its own
`FM2/CMakePresets.json` (binary dir `FM2/out/build/<preset>`) and either `add_subdirectory()`s this
SDK's source tree (`REXSDK_DIR` cache var) or `find_package(rexglue)` against an installed SDK.
`FM2/src/` is hand-written; `FM2/generated/` is regenerated via `cmake --build --target fm2_codegen`
(shells out to `rexglue codegen fm2_manifest.toml`); `FM2/out/` is pure build output.

## Code style

`.clang-format` (Google base, 100-col, 2-space indent) and `.clang-tidy`
(`HeaderFilterRegex: 'include/rex/.*'`) are authoritative — run `rex-format`/`rex-lint` rather than
guessing. Header-only public API lives under `include/rex/`; implementation lives under matching
paths in `src/` (e.g. `include/rex/kernel/xam/` ↔ `src/kernel/xam/`).

## Architecture

### 1. The `rexglue` CLI and codegen pipeline (`src/rexglue/`, `src/codegen/`)

`src/rexglue/main.cpp` builds a CLI11 app and registers subcommands, each populating a single
`DeferredAction pending` closure invoked once after arg parsing:

- **`codegen [manifest.toml]`** (`commands/codegen_command.cpp`) — the main entry point. Auto-
  discovers a `*_manifest.toml` in the cwd if no path is given, transparently migrates legacy
  single-binary TOML configs to the current manifest format, then calls
  `rex::codegen::ProjectRecompiler::Run`.
- **`init [--project-name --xex-path --game-root]`**, plus **`init module`** / **`init achievements`**
  (`commands/init_command.cpp`) — scaffolds a new downstream project from
  `resources/templates/init/*.inja` (this is how `FM2/` was created), appends a module to an
  existing manifest, or dumps XDBF achievement/icon data from a XEX into `achievements.toml`.
- **`recompile-tests --bin-dir --asm-dir --output`** (`commands/test_recompiler.cpp`) — the engine
  behind the `tests/ppc` self-hosting test pipeline described above.

Data flow for `codegen`: load the manifest → boot a `rex::Runtime` in tool mode → load the XEX/DLL
to get a `BinaryView` → run ordered analysis phases from `include/rex/codegen/phases.h`
(**Register** imports/config → **Scan** branch targets/thunks → **Discover** function
blocks/vtables → **GapFill** → **Merge** jump resolution → **Validate**) → each `FunctionNode`
decodes PPC instructions (`src/codegen/ppc/`) and dispatches to per-category C++ emitters
(`src/codegen/builders/{arithmetic,comparison,control_flow,floating_point,logical,memory,system,vector}.cpp`)
→ `CodegenWriter` renders the result through Inja templates (`resources/templates/codegen/*.inja`,
embedded into the binary at build time — see `cmake/embed_templates.cmake`) to emit
`{project}_init.{h,cpp}`, `{project}_register.cpp`, size-split `{project}_recomp.N.cpp`, and a
`sources.cmake` listing everything for the consuming project's build.

Manifest format (`include/rex/codegen/manifest.h`, TOML via `thirdparty/tomlplusplus`):
`[project]` (name, `sdk_version` pin, `game_root`), `[entrypoint]` and `[[modules]]` (each a
`BinaryConfig`: `file_path`, `out_directory_path`, analysis tuning, `[functions]` /
`switchTables` / `midAsmHooks` manual overrides for cases the analyzer can't resolve on its own).

### 2. Recompiled-code runtime layer (`include/rex/ppc/`, `src/kernel/`, `include/rex/kernel/`, `include/rex/memory/`)

Every recompiled guest function has the signature `void(PPCContext& ctx, uint8_t* base)`. `PPCContext`
(`include/rex/ppc/context.h`) is a flat struct holding all GPRs/FPRs/VMX128 vector registers plus
`lr`/`ctr`/`xer`/condition registers — the recompiled IR already did PPC semantic work, so register
fields hold host-native values. `base` is the host pointer backing the guest's flat 32-bit address
space; a guest address `addr` is simply `base + addr`.

**Endianness matters at every boundary crossing**: guest memory is big-endian (original Xbox 360
layout), the host is little-endian x64. Guest memory loads/stores and kernel-shim arguments are
explicitly byte-swapped (`rex::be<T>`, `memory::load_and_swap`/`store_and_swap`) — register values
inside `PPCContext` are not swapped, only what crosses into guest memory or emulated ABI args.

Kernel shims mirror the real Xbox 360 export surface: `xboxkrnl` (core NT-like kernel: threading,
sync objects, memory, I/O, HAL, crypto), `xam` (Xbox Application Manager: profiles, content/STFS
packages, achievements, input, net — `src/kernel/xam/apps/` covers XGI/XLiveBase/XMP-style service
apps), `xbdm` (debug monitor stubs), `crt` (C-runtime heap/string/memory shims). Each export is
defined via `REX_EXPORT(name, fn)` (`include/rex/hook.h`), which marshals `PPCContext` registers to
typed C++ args and self-registers by name — because recompilation is static, these are resolved at
recompile/link time rather than dispatched through a runtime import table at every call.

`src/system/xam` (and `system/achievement_manager.cpp`) hold the actual host-side service
implementations (profile/content/achievement state) that the guest-callable `kernel/xam` shims
delegate to — treat `kernel/*` as the ABI-facing shim layer and `system/*` as the real logic behind it.

The virtual file system (`src/filesystem/`, `include/rex/filesystem/vfs.h`) mounts `Device`s
(host path, disc image, STFS container, null) that back the recompiled game's disc/content reads —
this is what a game's file I/O actually resolves through, not raw host filesystem calls.

### 3. Platform backends — three different wiring patterns per subsystem

- **Graphics** (`src/graphics/`, `include/rex/graphics/`, `include/rex/ui/{d3d12,vulkan}/`) is the
  odd one out: it's a **runtime-loaded plugin** (`rexgpu-xenos.dll`/`.so`), not linked into the main
  binary. `REXGLUE_USE_D3D12`/`REXGLUE_USE_VULKAN` (root `CMakeLists.txt`) gate which backends
  compile into that plugin; which one activates is chosen at runtime by the `gpu_plugin` cvar
  through a versioned C ABI (`include/rex/system/gpu_plugin.h`, loaded via
  `src/system/gpu_plugin_loader.cpp`). The Xenos (Xbox 360 GPU) PM4 command stream is executed by
  `CommandProcessor`; shader microcode is cross-compiled by `ShaderTranslator` subclasses —
  `DxbcShaderTranslator` (D3D12, via vendored `dxbc`) or `SpirvShaderTranslator` (Vulkan, via
  vendored `glslang`/`spirv-tools`).
- **Audio** (`src/audio/{nop,sdl}/`) and **input** (`src/input/{mnk,nop,sdl,xinput}/`) are
  statically linked — every backend compiles into the same binary, selected/combined at runtime.
  Input in particular is **additive, not exclusive**: `CreateDefaultInputSystem`
  (`src/input/input_system.cpp`) stacks sdl-or-xinput (per `input_backend` cvar) plus `mnk`
  (keyboard/mouse-as-gamepad) plus a `nop` fallback, merging polled state across all active drivers.
  `xma/` is not a backend but Xbox's XMA audio codec, decoded via linked FFmpeg.
- **UI overlay** (`src/ui/overlay/`) is the in-game dev/debug UI (achievements, console, debug
  stats) — Dear ImGui-based (`thirdparty/imgui`), rendered through the same `ImmediateDrawer`
  abstraction both graphics backends implement, so overlay code itself is backend-agnostic.

When adding a new backend for any of these subsystems, match the wiring pattern of its siblings
(plugin ABI for graphics; static multi-driver stacking for input; single static implementation
choice for audio) rather than inventing a fourth pattern.

### 4. Vendored dependencies

`thirdparty/` is vendored source (added first in the root `CMakeLists.txt`, before warnings are
enabled for first-party code). Notable ones: `catch2` (tests), `cli11` (CLI parsing), `fmt`/`spdlog`
(formatting/logging), `tomlplusplus` (manifest parsing), `inja` (codegen templates), `imgui` (dev
overlay), `dxbc`/`dxc`/`glslang`/`spirv-tools`/`spirv-headers` (shader cross-compilation),
`FFmpeg`/`ffmpeg-overlay` (XMA audio decode), `sdl3`, `volk`/`vulkan-headers`/`vulkan-memory-allocator`,
`tracy` (profiler), `xxHash`, `snappy`, `libmspack`, `renderdoc` (capture API), `disasm`, `pe`
(PE parsing), crypto libs (`aes_128`, `tiny-aes-c`, `picosha2`, `crypto`).
