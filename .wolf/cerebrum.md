## Key Learnings (2026-07-04 — shader cache internals, black-texture root cause SETTLED)
- **FM2/generated/shader_cache.cpp stores DXIL *libraries*, not standalone shaders.** Each DXBC container has parts `SFI0,VERS,RDAT,HASH,DXIL` and NO `PSV0/ISG1/OSG1`. Runtime `LoadShader`→`LinkShaderLibrary(lib, dxil_off, type, specializedValue)` (pipeline.cpp) links per `spec_constants_mask` into a NEW standalone DXBC with a NEW DxilShaderHash. ⇒ a RenderDoc-presented DXIL hash is a LINK-TIME output and will NEVER match any cache entry's hash/bytes. Don't conclude "not in cache ⇒ fallback/miss" from a hash mismatch.
- **To tell if a cached shader samples textures, parse its RDAT ResourceTable** (NOT the DXIL bitcode — dx.op intrinsic names are not ASCII-visible there). RDAT: hdr {u32 ver,u32 partcount} + u32 part offsets; part type 3 = ResourceTable {u32 count,u32 stride=32} then records {class,kind,id,space,lb,ub,nameoff}; class 0=SRV,1=UAV,2=CBV,3=Sampler; names in part type 1 StringBuffer. Texture shader = has Sampler + SRV(Texture2D) `g_*DescriptorHeap`; color-only = CBV `SharedConstants` only. Scripts: scratchpad check_bg.py / rdat.py (zstd CLI decompresses g_compressedDxilCache → 1215408 B).
- **Black-texture root cause SETTLED:** bg guest PS `9E93B37448CA0172` is genuinely color-only (RDAT = CBV only) and links to presented `1b2db2c8`. XenosRecomp translation is CORRECT. The bug is plume handing the WRONG guest PS to textured draws (selection/context-routing), NOT translation, NOT texture-binding, NOT drop-latch/pacing. Investigate what writes the context PS slot ctx+0x307C per-draw.

## Key Learnings (2026-07-05 session — car position blow-up follow-up, bug-081)
- renderdoc MCP `get_texture_image` ignores `max_dimension` in practice (always returned full native res in this session) and its response (base64 PNG + stats) reliably exceeds the inline token cap for any real screen-sized RT — it always saves to a tool-results file. Decode with a quick python (`base64.b64decode` -> write .png to scratchpad) then `Read` the PNG to view it; this is the fastest way to visually diff two captures' render targets.
- To find "which draw is X" in an unfamiliar capture with no debug markers: `list_draws_with_state` (saved to file when large — use python, not jq, since this Windows env has no jq), group by (vertex shader, pixel shader) resource-id pair, and look for shader pairs used only 1-3 times with distinctive vertex strides/index counts — one-off shaders are far more likely to be a specific gameplay object (car, logo) than the shaders reused hundreds of times (those are UI/text/particles).
- `get_frame_overview`'s `render_targets` list only surfaces ONE target (looked depth-biased in both FM2 captures) — it is not a complete list of color RTs. To find the real color backbuffer, tally `color_targets` across `list_draws_with_state` and take the resource used by the most draws.
- RenderDoc's own "Colour Pass #N" numbering (as seen in the UI) is a UI-only heuristic (EventBrowser pass detection), not exposed by the MCP tools directly — approximating it by grouping draws on (color_target, depth_target) tuples is the closest available reconstruction, but don't over-index on getting the exact number right; confirming the actual draw via shader/mesh fingerprinting + `debug_vertex` NDC math is more reliable than matching the pass index.
- `debug_vertex`'s `final_registers._OUT.SV_Position` is clip-space (x,y,z,w) — compute NDC as x/w, y/w yourself; RenderDoc does not do it for you. `nan_or_inf_steps: []` does NOT mean the position is correct — it can still be a finite-but-wrong value (a milder, non-poison mistranslation) as seen in bug-081, distinct from bug-072's ±FLT_MAX poison pattern.
- Some .rdc captures have shader disassembly UNAVAILABLE for every shader in the capture (not our MCP's fault, not the bug-073 sentinel issue): `get_shader(include_disassembly=true)` fails with "could not resolve this shader's resource for disassembly (replay-side resource-tracking gap for this shader's creation path)", and `list_resources` shows those shader ids as `name:"" type:"Unknown"` (PipelineState objects still get proper names). Test on 2-3 different shaders in the SAME capture before concluding it's capture-wide vs. one-off; if capture-wide, full_trace debug_vertex still works (gives register values) but you lose the actual instruction text — you're limited to inferring the operation from value patterns (ratios, swaps, proportionality to known quantities like clip-space W) plus reading the XenosRecomp fork source directly as a substitute for disassembly.
- `debug_vertex(full_trace=true, full_trace_path=<file>)` writes `{stage, inputs, constant_blocks, disassembly, steps}` to disk — `steps[i].disassembly` is usually empty per-step; the top-level `disassembly` list is also empty when disassembly is unavailable for the capture (see above). Don't rely on it; use `steps[i].changes` (register name+value at each step) instead.
- xenia-canary source (for cross-checking XenosRecomp's ALU lowering) lives at `C:\Users\Tera\Documents\GitHub\xenia-canary`; the actual filename is `src/xenia/gpu/dxbc_shader_translator_alu.cc` (memory notes calling it "dxbc_translator_alu.cpp" were an approximation — grep for `case AluScalarOpcode::k<Name>` to find a specific op's lowering).

## Key Learnings (2026-07-05 — RenderDoc<->on-disk shader mapping SOLVED)
- **Map a RenderDoc shader to its on-disk shader (the {hash}.hlsl / shader_cache.cpp entry) via the PSO NAME.** Problem: RenderDoc only sees the runtime-LINKED DXBC (its DXIL hash is a link-time output != the cache XXH64 key), and D3D12 shaders aren't nameable objects (plume `D3D12Shader::setName` is a documented no-op — "Nothing to set a name on"). SOLUTION: the PSO *is* nameable (`D3D12GraphicsPipeline::setName` -> `ID3D12PipelineState::SetName`, RenderDoc displays it). At the FM2 native pipeline-create site (render_state.cpp ~2112, `Device()->createGraphicsPipeline(desc)`), stamp `pipeline->setName("FM2 VS=%016llX PS=%016llX", ShaderHash(ps.vertexShader), ShaderHash(ps.pixelShader))`. `ShaderHash()` (render_state.cpp:601) returns `shaderCacheEntry->hash` = the guest XXH64 = the XenosRecomp `{hash:016X}.hlsl` filename. Every capture taken after this build self-identifies each draw's VS+PS on-disk hash — no log correlation, works retroactively on any post-change capture. Dump all shaders' HLSL with `XenosRecomp.exe --dump-hlsl FM2/assets <outdir> <shader_common.h>` (64 unique FM2 shaders).
- **Reusable evidence tool:** to read any FM2 shader's translated HLSL without RenderDoc, use the in-tree `XenosRecomp --dump-hlsl`. Combined with the PSO-name mapping, the loop is: RenderDoc draw -> PSO name -> VS/PS hash -> `.cache/fm2_hlsl_dump/<hash>.hlsl`.

## Key Learnings (2026-07-05 — RenderDoc CORE bug found+fixed+rebuilt, bug-087/088)
